# Interface examples and limits

Read for interface creation or cleanup when context affects what to keep. These examples come from the user's reviews of several products. They show decisions, not strings to copy into unrelated projects. 

## Remove repetition across the visible screen

**Observed request:** In a directory, “Call the mikvah to arrange your time” repeated the call-for-appointment action. The user asked to remove it and keep useful address information.

**Apply:** Keep the action. Delete the explanatory sentence when it adds no conditions. Keep actual appointment conditions if they change the visitor's choice. An address is useful even when raw map coordinates are not.

**Observed request:** Remove “Directory book” above the obvious book section, “Your home address” above the actual recipient, and “BUSINESS INFORMATION” above obvious details.

**Apply:** Let concrete content identify the section when that is clear. Keep headings that support navigation or distinguish similar groups. Do not remove semantic structure merely to make the screen look sparse.

## A number must help this task

**Observed request:** Delete “65 sourced,” including other count variants, with no replacement.

**Observed request:** Remove a missing-bill count from the bill-entry flow. The user was entering a bill, not looking for missing bills.

**Apply:** Ask what decision the number supports. The same missing-bill count might be useful on a reconciliation screen. Do not delete it there based only on this example.

**Observed request:** “Select all 84” duplicated “84 people.” The user wanted to rethink the control.

**Apply:** A labeled checkbox may carry the action without repeating the count. Preserve selection scope. If 84 means all results but only 20 are visible, that distinction may need text. Do not drop a number until its meaning is known.

**Observed request:** Put the like count in the like action instead of showing a separate count and button.

**Apply:** Combine value and action when both stay clear and accessible. Do not replace a clear control with an unexplained number.

## Show information when it becomes useful

**Observed request:** Remove the avatar's persistent “JPEG, PNG, or WebP” text. Replace the pre-submit review explanation with “Sending,” then “Pending review,” beneath the submitted message.

**Apply:** Show the correct state at the correct time. Do not claim “Pending review” before the server accepts the message. Retain a helpful file-type error if an unsupported file is chosen. Keep restrictions visible beforehand if they impose a material cost on choosing or preparing a file.

**Observed request:** The user rejected lots of scanner instructions and empty sections. After cleanup, the user requested useful empty-state text and “Scanner ready.”

**Apply:** The initial state still needs a purpose, readiness, and a clear way to begin. Results and totals should appear when there are results. Do not hide an unavailable scanner or leave an unexplained blank panel.

## Keep useful ways to start

**Exact user target:** “No attachments yet” and “Drag and drop any file here.” The user allowed an Upload File button and wanted it to open the native picker immediately.

**Apply:** Different input methods can be useful even when they reach the same result. Keep the button for people who cannot or do not want to drag files. Use an accurate restriction if the product does not accept any file.

**Observed request:** A first-use a commentary reader guide should explain the marks, colors, and commentary model, and be available again later.

**Apply:** Put an unfamiliar model in a short guide or appropriate help. Daily screens need not repeat the guide. Keep the source-versus-proposal distinction beside the content when it affects interpretation.

## Use the product's language

**Observed request:** Replace conversational field prompts such as “give it a name” and “who carries it” with the established fields, including “Vendors.”

**Apply:** Name fields plainly. Use the existing singular or plural convention. Do not rename a product concept because a synonym sounds friendlier.

**Observed request:** Remove sales-setting subtitles such as “A slower steadier read.” Show actual dates and useful controls. The user later refined fixed “Sold in past” text because the selected period already supplied the time context.

**Apply:** Test the full label with values such as “This week,” “Last two weeks,” and a named season. Do not shorten a value until date scope and units remain clear.

## Fix false states at the source

**Observed request:** A search showed “No contacts match” immediately after a person was added. The user objected to the state and asked for the search behavior to make sense.

**Apply:** If the product filters out people who already have access, do not label that as no matching person. Within authorized scope, clear the completed search or show accurate access state. If the task is copy-only, explain the behavior issue and provide wording only for states whose meaning is known.

**Observed request:** “Not in this reading” was wrong because the displayed material was the original source.

**Apply:** Verify the underlying meaning. A shorter synonym would not fix the error.

## Do not turn examples into banned-word lists

The user rejected “Coming soon” on one an inventory app chatbot screen and explicitly requested it for an unavailable a planned language recorder option.

The user rejected “Prints in two business days” in one certificate order flow. That does not authorize removing a delivery promise required for another purchase.

The user removed a local test code and prototype explanation from normal product UI. Keep testing context separate, but do not disguise an unavailable or simulated operation as a completed real action.

The user asked to compare microphone labels but did not select a final winner. “Shared microphone” is an example of a noun phrase, not recorded approval of that label. Inspect what the toggle changes before choosing wording.

## Evidence strength

The user explicitly approved removal of the master-directory subtext, then continued correcting the dropdown layout. The user liked the Split filter direction and “Filter suggestions,” but rejected the subtitle.

These are local approvals. They do not establish approval of every element on those screens. Other examples here are requested targets or corrections, not claims that the final implementation was accepted.
