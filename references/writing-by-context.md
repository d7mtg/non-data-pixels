# Writing by context

Read when writing outside routine interface labels. The user's style changes with the reader and purpose. Preserve the information the form needs.

## Articles and explanations

Introduce the subject before the argument. Tell an unfamiliar reader what the object or topic is, where and roughly when it belongs when relevant, and why it deserves attention. Use an appropriate real image when the assignment calls for one. Then explain the evidence or question in connected prose.

The user rejected impersonal openings, too many sentence breaks, and articles that assumed readers already knew the subject. The user also removed slogans, reading-time labels, redundant dates, and crowded article headers. These are compatible preferences: meaningful article context stays; routine page decoration can go.

Use natural transitions where the ideas need them. Let sentence length and paragraph structure carry the argument. Prefer direct openings; use a comparison or question when it clarifies the subject. Cut conclusions that only repeat what the reader already understands.

Do not fabricate first-person memories to create a human voice. The user's example of a personal introduction illustrates narrative flow, not permission to invent a visit or discovery. Ground any anecdote in supplied facts. Retain sources, uncertainty, and distinctions needed for accuracy. Do not erase them as “slop.”

For a routine text edit, keep the facts supplied. Research only when the task or unresolved factual issue requires it. Do not turn copy cleanup into unrelated research.

## Marketing and onboarding

A clear benefit is useful. A slogan that could fit any product usually is not. Say what people can do with this product and why that capability matters. Use the product's own terms and actual features.

The user requested a useful marketing line with a few features on a sign-in screen. The user also requested an onboarding story that advanced from building a list, through adding people, to printing.

A short heading and a natural sentence may be enough. Do not force all marketing into bare field labels. Avoid extra subtitles, staged revelations, grand claims, and invented reasons the reader should care. Do not add urgency, proof, customers, or outcomes without evidence.

When multiple steps form one flow, let each step add new information. Do not repeat the product introduction on every step. Keep mandatory action conditions visible where users need them.

## Client updates and handovers

Match the sender and the purpose. For an individual reporting completed work, first-person singular and past tense often fit: “I added,” “I changed,” “I removed.” Use “You can now” for a confirmed new capability when useful. A team update or a different requested voice may call for another perspective. Use present tense for current behavior.

The user rejected “Select all waits for the full list and lands once.” The objection concerned the subject, tone, jargon, and lack of a useful client-facing change. The user asked for active statements of what was done or what the client can now do.

Group work by a screen or flow the client recognizes. Include relevant new work as well as changes. Do not make every delivery a change list when it is a new feature handover.

Use evidence to distinguish a design, implementation, and live release. “I designed the reset flow” must not become “I added password reset” if no working feature exists. Omit discarded approaches, duplicate items, source provenance, internal task IDs, agent process, and private collaborator details unless the user asks for them. Keep real delivery limits clear.

Questions should invite useful information. The user found “The sentence is cut off. Please finish it” aggressive and requested a happy, curious tone. A suitable new example is “What happens after this?” Use plain warmth without adding praise or baby talk.

If the task is a full client handover and the installed `client-handover` skill is available, use it for the document format and delivery workflow. This skill adds copy judgment; it does not override the requested file type or create permission to send the document.

## Specifications, manuals, and working documents

Describe the current system for a fresh reader. Keep necessary unresolved decisions and distinguish intended behavior from implemented behavior. Remove abandoned approaches and discussion of what the previous document said unless version history is the requested purpose.

The user called accumulated old versions an “archeological dumping site.” A current specification should not read like a transcript of its creation.

For instructions, use a direct action and include a result only when it helps the reader continue. Replace personification such as “The door asks two things” with actual login actions. The historical assistant's proposed steps were not explicitly approved; direct action is the supported principle, not a fixed template.

Do not confuse concise documentation with missing setup, prerequisites, or recovery steps. Keep the details required to perform the task. Use the reader's terminology; explain an unfamiliar technical term only if the reader needs it.

## Replies in chat

Lead with the useful result. Match length and detail to the question, the reader, and the current instructions. Use paragraphs, lists, and emphasis where they help. State material limits plainly. Put a long report in a file when that is requested or makes it easier to use.

Cut commentary that only announces the cleanup, repeats the answer, or adds a generic offer. Include a next step or summary when it serves a real need. Choose wording and punctuation for clear reading rather than to satisfy a style checklist.

There is no fixed sentence or line limit. A short status update and a detailed explanation need different amounts of text. The measure is whether each part helps the reader.

## Keeping preferences accurate

These rules come from repeated product reviews. Examples distinguish requested wording, specific approval, continued criticism, and unconfirmed changes.

When the user gives a new task-specific preference, apply it. Do not overrule it with an older example. Do not record silence, a new topic, or an assistant's success claim as approval. Keep provenance outside client-facing deliverables.
